1단계: 인증키 없이 결과 확인

압축을 풀고 프로젝트 폴더에서 다음 명령을 실행합니다.

python -m pip install -r requirements-core.txt
python -m jachi.cli demo --out output/demo_report

output/demo_report.md와 .json이 생성됩니다. 이는 가상 자료이며 실제 자치법규를 검증한 결과가 아닙니다.

2단계: 공식 자료 연결

requirements.txt를 설치하고 본인의 국가법령정보 공동활용 API 인증값을 LAW_OC 환경변수에 설정합니다. .env.example에 적는 것만으로 적용되지 않습니다. 먼저 scripts/live_check.py, 이어서 scripts/smoke_mcp.py를 실행합니다. 자세한 PowerShell 명령과 Render 설정은 배포 안내를 따릅니다.

첨부 원본의 Render 설정은 의회회의록 서버를 시작하도록 되어 있었습니다. 기존 회의록 서비스가 운영 중이라면 그 저장소를 덮어쓰지 말고 조례 전용 저장소·서비스로 배포하세요.

3단계: 실제 조례를 골라 종합 검토

정식 기관명·조례명·공식 ID를 먼저 확인하고, 기준 조례와 비교 조례, 상위법을 지정합니다. 검색 첫 결과를 기준 조례로 확정하지 않습니다. 자동 수집의 비교 기관은 최대 4곳의 탐색 표본이며 우수 조례 순위나 전수조사가 아닙니다.

MCP 연결 후 다음처럼 업무를 설명할 수 있습니다. 아래는 요청 예시일 뿐, 해당 사업을 이미 검토했다는 뜻은 아닙니다.

주민 참여에 따른 포인트 지원 사업을 검토하고 있습니다. 우리 기관의 관련 조례와 다른 기초자치단체 조례를 공식 자료로 찾고, 기존 근거 활용·일부개정·별도 제정 중 어떤 방향을 검토해야 할지 8개 역할로 분석해 주세요. 지원대상·재정·신청과 선정·중복지원·개인정보·성과평가의 차이와 확인이 필요한 근거를 구분해 주세요.

지정한 상위법의 구·신 버전을 비교하고, 우리 조례에서 바뀐 조문을 인용한 부분을 찾아 정비 후보와 신구대비 초안을 제시해 주세요. 시행예정·부칙·별표 미확인 사항은 별도로 표시해 주세요.

사용 전에 알아야 할 한계

초안은 검토용이며 자동 결재·제출·공포하지 않습니다. 원문 인용이 맞아도 법적 취지·위임 범위가 맞는지는 별도 확인해야 합니다. 별표 파일 본문 자동 수집, PDF·HWP·HWPX 직접 입력, 판례·의견제시 통합 분석, 모든 간접 개정 영향, 기관 SSO는 이번 버전의 구현 범위가 아닙니다.

변경 감시 명령은 1회 실행 후 종료합니다. 정기 실행·알림·영속 저장소는 운영자가 따로 설정해야 합니다. 비공개 문서·개인정보를 입력하지 말고, 외부 AI 사용과 배포 전에 기관 보안·법무 기준을 확인하세요.

작성 기준: 2026년 9월 22일 / 대상: 첨부 jachi-mcp-main.zip / 산출물: v2.0.0-rc.1

1. 개선 방향

조례의 조항 수를 늘리거나 비슷한 조례를 많이 보여주는 것만으로는 입법업무를 충분히 도울 수 없다. 신규 사업이 기존 근거로 가능한지, 별도의 입법이 필요한지, 타 기관 사례가 우리 기관의 권한과 재정에 맞는지를 함께 검토해야 한다.

본 개선판은 자료 수집, 적용시점 확인, 기능 비교, 상위법 인용 확인, 정비 후보 발굴, 집행 절차 검토, 초안 작성, 근거 감사를 하나의 흐름으로 묶었다. 불완전한 자료를 완전한 것처럼 다루지 않으며, 검토 후보와 법적 결론을 분리한다.

3. 8개 역할의 책임과 산출물

역할 핵심 질문 산출물 다음 역할에 넘기는 사항
A1 사업·입법기획 무엇을 해결하며 조례가 필요한가? 사업 설명, 검토 방식, 필요한 자료 사업 목적·기관·검색어·검토 기준일
A2 공식자료·버전관리 어떤 문서의 어느 버전을 확보했는가? 문서 원장, 조회 상태, 범위, 선택 기록 공식 원문·근거 ID·미수집 항목
A3 상위법·권한검토 소관사무·위임·법률유보를 확인했는가? 규칙별 확인 항목, 인용 조문 존재 여부 권한·근거·미확인 인용사항
A4 지자체 비교 기능이 실질적으로 어떻게 다른가? 대응 후보, 기능 매트릭스, 수치·의무 차이 도입 검토 후보와 대응 원문
A5 개정영향·연계정비 상위법 변경이 어디에 영향을 주는가? 구·신 차이, 직접 인용 조례의 정비 후보 부칙·별표·규칙·업무의 연계 확인
A6 재정·절차·집행 돈·인력·절차·시스템이 준비되는가? 조건부 사전협의 목록, 비용추계 틀 적용 여부 미확정 절차·협의 사항
A7 입안·개정안작성 어떤 형식과 내용이 적절한가? 제안이유 틀, 조문 골격, 모델 선택 시 조문 제안 미확인 조건 및 근거가 연결된 제안
A8 반대검토·근거감사 빠진 근거·상충·시점 오류가 없는가? 미확인·오류·보류 목록 최종 담당자 검토표

실행 순서는 A1 → A2 → A3~A6 병렬 단계 → A7 → A8이다. A7에는 법적 검토사항, 인용 확인, 개정 영향, 절차 의존사항을 전달한다. Gemini 모드에서는 A7·A8에 선행 역할의 인용 검사 결과와 반대 의견도 전달한다.

규칙 모드는 실제 외부 LLM 8개가 아니다. 외부 모델 모드는 역할마다 생성 요청을 별도로 수행하지만 같은 모델의 역할 분담이다. 어느 방식이든 다수결로 적법성을 확정하지 않는다. A8 자신의 모델 인용 오류도 최종 검토표에 다시 반영한다.

4. 사업 설명에서 입법 검토로 연결

단순히 사업명 뒤에 “지원 조례”를 붙이는 방식을 사용하지 않는다. 다음 대안을 순서대로 살핀다.

대안 판단을 위해 필요한 자료
기존 근거 활용 현재 소관사무·대상·지원방식·예산·집행절차가 사업을 포함하는지
기존 조례 일부개정 기존 목적 안에서 대상·사업·기준·절차의 정비로 해결되는지
별도 조례 제정 독립적인 규율 필요성과 중복 방지, 권한·위임·재원·효과가 설명되는지
규칙·지침 정비 위임받은 집행 세부사항인지, 본질적 사항을 부당하게 낮은 형식으로 정하지 않는지
사업 재설계·유보 권한·상위법·재원·협의·효과 측면의 장애가 해소되지 않았는지

예를 들어 주민 참여에 포인트를 제공하는 사업은 지원 근거, 대상, 지급 방식, 예산, 중복 지급, 운영상 개인정보, 중립성 관련 검토 필요성을 확인하도록 한다. 이 예시는 해당 사업의 적법·위법 판단이 아니라 검토 질문을 구조화한 것이다.

5. 비교 방법과 해석 한계

12개 비교 영역은 목적·정의, 소관사무·책무, 지원대상·제외, 지원내용·금액, 신청·선정, 지급·중복방지, 중지·환수·이의, 위원회·제척회피, 위탁·공유재산, 개인정보·기록, 점검·평가·공개, 시행·경과·서식이다.

대응 후보는 제목, 본문 3글자 집합, 기능 단서를 가중 결합하여 찾는다. 그 값은 검색 유사도이며 법적 적합성 점수가 아니다. “할 수 있다”와 “하여야 한다”, 지원금액, 연령·기간·인원, 제외·포함·상하한 차이는 별도 표기한다. 제목이 없거나 같은 제목이 여러 번 나와도 조문을 버리지 않는다.

possible_gap은 실제 누락 확정이 아니다. 다른 조문·다른 조례·상위법에서 이미 규율하거나 해당 기관에는 불필요할 수 있다. 광역·기초·교육기관의 권한 차이도 별도 확인한다. 자동 수집은 최대 4개 기관의 탐색 표본이며, 인구·재정규모·정책 성과를 종합한 우수사례 순위가 아니다.

과도한 연산을 막기 위해 기본 24,000개의 조문 쌍 비교 한도를 둔다. 한도를 넘으면 비교하지 못한 조문 수를 명시한다. 기능 매트릭스 관측과 조문 정밀 대응의 완료 여부를 구별한다.

6. 상위법 개정과 적용시점

현행 시행일 기준 조회는 eflaw, 공포일 기준 조회는 law로 분리한다. 시행일 기준에서 ID를 쓰면 현행본 조회가 되므로 과거·특정 버전 조회는 MST+efYd를 사용한다. 명시 버전 조회 시 ID와 MST를 동시에 보내지 않는다. 공식 API 계약은 출처 문서 S04~S07을 참고한다.

as_of는 검토 기준일이다. 이 값을 과거로 바꾸는 것만으로 자동으로 과거 법령을 복원하지 않는다. 과거 시점 검토에는 해당 버전의 식별자·시행일을 별도로 확보해야 한다. 본문 전체 시행일만으로 조문별 특례·부칙까지 확정하지 않는다.

구·신 버전에서는 신설·삭제·본문 변경, 조번호 이동 가능성, 부칙·별표 변화, 제명·시행일 변화를 확인한다. 조례 안의 명시 법령명·조번호가 변경 조문과 연결되면 우선 검토 후보로 표시한다. 직접 인용하지 않은 조례의 간접 영향은 완전하게 탐지하지 못한다.

반복 점검은 지정된 ID의 조회본과 직전 성공본의 비교다. 시행일 기준과 공포일 기준을 별도 저장한다. 최초 실행은 기준 저장이고 과거 개정 전수 분석이 아니다. 데이터 오류·통신 실패·해석 실패 시 기존 기준본을 유지한다. 스케줄러와 알림 전송 자체는 운영자가 따로 연결한다.

7. 제정·개정 초안의 안전장치

기본 모드는 목적·정의·적용범위·사업·신청·재정·관리·권익·부칙의 검토 골격을 만든다. 각 조문이 반드시 필요하다고 결정하지 않으며 불확실한 근거·대상·시행일은 대괄호로 남긴다.

Gemini를 명시적으로 사용한 경우 A7은 사업별 조문을 제안할 수 있다. 조문 구조와 번호, 근거 ID, 인용문을 확인한다. 존재하지 않는 근거를 인용하거나 조번호가 맞지 않는 제안은 채택 목록에서 제외한다. 인용이 맞더라도 입법 권한·위임 범위·재정·시행 가능성이 검증된 것은 아니다.

일부개정문은 별도의 jachi_draft_amendment에서 만든다. 기준 원문 SHA-256과 expected_text가 정확히 일치해야 한다. 한 조문에 두 작업을 동시에 적용하거나 존재하는 조번호에 다시 신설하지 않는다. 삭제 시 번호를 없애 뒤 조문을 당기지 않고 “삭제” 상태로 남긴다. 자동 조번호 재배치와 본문의 모든 단어 일괄 치환은 하지 않는다.

개정문, 변경 전·후 대비, 변경 이유, 근거, 변경 미리보기를 제공하며 공포·의결·전자결재 전송은 하지 않는다.

8. 근거 중심 결과 구조

모든 조문 근거에는 문서 종류, 공식 ID, 버전, 기관, 조문키, 원문, 공개 출처 주소, 조회시점, 시행일, 자료 상태, 내용 해시가 연결된다. 자료 상태는 공식 실조회, 캐시, 오래된 자료, 사용자 제공, 시험자료를 구별한다. 외부 입력으로 “검증 완료” 상태를 지정할 수 없다.

인용 검사는 등록된 근거 ID인지, 인용문이 그 원문에 그대로 있는지를 확인한다. 그 문장이 주장 전체를 뒷받침하는지, 법적 해석이 맞는지까지 증명하지 않는다. 출력에 semantic_entailment_verified=false, legal_validity_verified=false를 유지한다.

9. 아직 완료되지 않은 범위

실제 MCP SDK 연결, 이 패키지의 공식 API 실응답, Gemini 실제 생성은 제작 환경에서 검증하지 못했다. 시험 자료와 모의응답이 실제 전국 자치법규의 모든 형식을 대표하지도 않는다. RC를 운영에 반영하기 전 실제 자료로 확인해야 한다.

자치법규 별표 API는 제공 범위가 제한된다. 별표 파일의 표·수치·서식 본문 자동 다운로드·변환은 구현하지 않았다. PDF/HWP/HWPX 입력, 판례·의견제시 자동 통합조회, 상위법의 모든 간접 영향, 기관별 절차 조례의 완전 자동 판독도 구현 범위 밖이다. 외부 모델의 제안만으로 이를 완료했다고 표시하지 않는다.

법무 담당자와 실무부서가 실제 제정·개정 사례를 골라 기존 검토 결과와 비교한 뒤, 오탐·미탐을 수정하고 운영 승인을 거쳐야 한다.

2. 실행 환경

Python 3.13.5, Linux. 확인된 패키지는 httpx 0.28.1, pydantic 2.13.4, defusedxml 0.7.1, uvicorn 0.48.0이다. MCP SDK는 미설치이며 공식 API·Gemini 인증값 없이 시험했다. 키 자체는 기록하지 않았다. docs/qa/environment.json에 설정 여부만 남겼다.

Python 3.11·3.12용 CI 설정은 작성했지만 이 제작 환경에서 해당 두 버전으로 실행한 것은 아니다. 의존성은 호환 범위로 지정했으며 설치된 전체 패키지를 잠근 공급망 검증 완료 환경은 아니다.

3. 어떤 실패 상황을 시험했는가?

수집과 원문: 단일 객체 응답, JSON/XML, 한글 인코딩, 장·절 제외, 항·호·목 보존, 가지조문, 부칙·별표 메타데이터, 중복 조번호, HTTP 200 오류 본문, XML 외부 엔터티, 비정상 대용량 응답, 리다이렉트 차단을 확인했다.

대상과 범위: 다른 기관·다른 제명·다른 ID/MST의 혼입, 검색 결과 반복, 전체 건수와 페이지 불일치, 한도 도달, 실패와 0건 구별, 명시적 키 설정과 재시도 한도를 확인했다.

분석과 입안: 조문 본문·기능·수치·의무 표현, 비교 연산 상한, 시행예정·과거 기준일, 조문·부칙 변경, 직접 인용 영향, 없는 인용 조문, 존재하지만 법적 취지 미확정 상태, 원문 해시 불일치, 기대 원문 불일치, 신설·대체·삭제 충돌 등을 확인했다.

협업과 모델: 8역할 실행, 8회의 별도 모의 모델 요청, A7 조문 제안의 형식과 인용 검사, 허위 근거·불일치 인용 제외, 개인정보 단서, 원문 속 지시를 데이터로 취급, A8 자체 오류를 최종 검토표에 반영하는지를 확인했다.

HTTP와 관측 이력: Bearer·Host·Origin, URL 인증값 거부, 본문·요청량 제한, 불안전한 공개 설정 거부, SQLite 재시작·변경·미변경, 시행일/공포일 관점 분리, 수집 실패 시 마지막 성공본 보존을 확인했다. ASGI 경계 시험과 실제 MCP 프로토콜 시험은 다르다.

4. 가상 데모 해석

예제는 가상 돌봄사업과 가상 조례 2건·가상 상위법 1건이다. 공식 법령 원문이 아니라 user_provided로 표시된다. 비교 결과에는 기능 차이 후보가 나타나며, 상위법 구·신 버전이 없으므로 개정영향을 완료하지 못했다고 표시한다. 최종 법적 승인과 제출 준비 상태는 false다.

이 데모의 역할은 결과 구조와 안전한 미확정 표시를 보여주는 것이다. 실제 광주 서구 조례에 특정 조문이 없다는 근거로 사용할 수 없다.

S03 자치법규 본문 조회 API ID/MST, 조문과 장·절의 구분, 부칙·별표 필드 안내상 별표 제공은 서울시교육청과 본청으로 제한. 별표 미수집을 명시
S04 현행법령 시행일 기준 목록 API target=eflaw 검색과 버전·시행일 확보 제명·ID를 확인하고 검색 첫 결과를 임의 채택하지 않음
S05 현행법령 시행일 기준 본문 API ID는 현행본, MST+efYd는 특정 시행버전 지정. 조문별 시행일·항호목·부칙 ID와 MST 동시 전송 금지. 기준일만 바꾸어 과거법 조회를 가장하지 않음
S06 현행법령 공포일 기준 목록 API target=law, 공포·시행 메타데이터 시행일 기준 검색과 별개 모드. 시행예정과 현행을 혼동하지 않음
S07 현행법령 공포일 기준 본문 API 공포일 기준 ID/MST 본문과 부칙·별표 감시 저장키에 조회 관점을 포함. 과거 중간 버전 전수 복원은 아님
S08 법령·조례 연계 관련 API 안내 법령 ID를 바탕으로 한 연결 조례 후보 탐색 연결 결과를 완전한 영향 범위로 보지 않음
S09 조문별 법령·조례 연계 관련 API 안내 법령 ID, 조번호·가지번호를 이용한 연결 후보 직접 인용을 별도 대조. 모든 간접 영향 탐지는 미구현
S10 법제처 자치법규 입안 길라잡이 소관사무·입법형식·상위법과의 관계·본칙·부칙·개정 방식 검토 입법 판단 항목을 구성한 참고자료. 법무심사 자동 승인 기능 아님
S11 법제처 자치법규 의견제시 사례 구체적인 사안별 권한·위임·형식에 관한 추가 확인 경로 사례 원문 자동 수집·정합성 분석은 이번 버전에 통합하지 않음
S12 자치법규정보시스템 ELIS 현행 자치법규·기관 확인의 공식 대조 경로 ELIS 전수 크롤러나 별표 파일 수집기가 구현되었다는 뜻은 아님

S03·S05의 명세에 조문과 별표 관련 필드가 존재하더라도 모든 기관·모든 문서에서 값이 완전하게 제공된다는 보장은 없다. 본 패키지는 빈 자료·응답 실패·한도 도달·역사적 버전 불명확을 구분해 남긴다. API 응답에 독립적인 ID/MST 확인 필드가 없으면 요청값만으로 독립 검증을 완료했다고 하지 않는다.

2. 국내외 도구에서 반영한 장점

ID·사례 공개 문서에서 확인한 접근 본 개선판에서 반영한 부분 반영하지 않은 부분
S13 Korean Law MCP 법령·판례·조례 조회, 인용 검증, 시점·개정 영향 조회, 자료 부재와 장애의 구분 근거 ID, 원문 인용 대조, 변경 전후 비교, 불완전 수집 표시, 호출 예산 해당 서버 코드·판례 Citator·모든 전문 분야 API의 통합·실행은 아님
S14 legalize CLI·MCP 사람과 에이전트가 함께 쓰는 구조화된 법령·판례·자치법규 조회 도구 핵심 로직을 CLI와 MCP에서 공유, 명시적 입력 모델·JSON 결과 외부 서비스 계정이나 저장소를 묶어 배포하지 않음
S15 OpenFisca 정책·법규 규칙을 코드로 표현하고 시점별 계산·시험을 수행 날짜·버전이 명시된 규칙, 변경 시험, 계산 가능한 판단과 확인 필요 판단의 분리 OpenFisca 엔진, 세금·급여·지원금 계산모형, 검증된 재정 시뮬레이션은 없음
S16 docassemble 질문과 조건을 통해 정보를 모으고 문서를 조립하는 방식 사업 설명의 구조화, 미확인 질문, 조건별 조문 골격, 신구대비 출력 docassemble 엔진이나 그 PDF·DOCX 출력 기능을 내장하지 않음
S17 OASIS LegalDocML / Akoma Ntoso 법률 문서의 구조·참조·식별을 명시하는 표준화 접근 본칙·부칙·조문키·버전·참조를 분리한 내부 문서 모델 Akoma Ntoso XML 입출력, 표준 준수 인증은 구현하지 않음
S18 MCP Python SDK 도구·리소스·프롬프트와 표준 전송 방식, 버전 이행 안내 명시적인 도구 설명·입력 스키마, STDIO/Streamable HTTP 구조 실제 SDK 프로토콜 연결은 이 제작 환경에서 미시험
S19 MCP 전송 보안 안내 HTTP Origin 검증, 로컬 바인딩, 인증 등 전송 경계 Host/Origin 제한, localhost 기본값, Bearer 인증 경계 OAuth 2.1·기관 SSO·사용자별 권한·분산 요청량 제어는 없음
S20 Gemini Structured Outputs JSON Schema에 따른 모델 결과 구조화 역할별 JSON 모델, 근거 필드, 형식 검사와 원문 인용 검사 분리 JSON 형식 준수를 법률적 정확성 보증으로 취급하지 않음
S21 Gemini GenerateContent API 모델 호출 경로·인증 헤더·생성 설정 고정된 API 경로, 역할별 호출 상한, 출력 한도, 선택 동의 실제 생성·요금·모델별 스키마 지원은 사용자 계정에서 확인 필요

3. SDK 버전 선택

S18 확인 시점에 공식 SDK의 현행 안정 계열은 v2이며, v1.x는 중요 오류·보안 수정이 유지되는 별도 계열로 안내된다. 원본의 FastMCP 기반을 유지하면서 의도치 않은 주요 버전 변경을 막기 위해 이 패키지는 mcp>=1.28,<2를 사용한다. “최신 v2로 이관 완료”라고 표현하지 않는다. 설치 후 tests/test_sdk_integration.py와 scripts/smoke_mcp.py를 반드시 실행한다.

4. 활용·재배포 경계

이 문서는 기능과 설계 원칙을 요약한 것이다. 외부 프로젝트 소스·공식 길라잡이 책자·별표 원문을 복제해 동봉하지 않았다. 관련 엔진을 의존성으로 추가한 것처럼 표시하지 않는다. 후속 개발에서 외부 소스·문서·데이터를 직접 복제하거나 배포할 때는 각각의 라이선스와 이용 조건을 따로 확인해야 한다.

이번 벤치마크는 서비스 설계·공식 API 계약 비교다. 전국 지자체의 실제 조례를 대량 수집해 정책성과를 비교한 연구 보고서가 아니다. 실제 조례 비교는 운영 시 확보한 문서와 확인된 범위에서 실행한다.
