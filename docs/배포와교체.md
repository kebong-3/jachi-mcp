# 배포·교체·실행 안내

## 1. 원본과 운영 서비스부터 확인

첨부본의 `render.yaml`은 회의록 서버 `uijeong_mcp.py`를 실행한다. 현재 Render 서비스가 실제 회의록 MCP라면 **그 서비스를 이 ZIP으로 덮어쓰지 않는다.** 조례 전용 저장소와 서비스를 따로 만들거나, 실제 교체 대상이 조례 서비스인지 먼저 확인한다.

이 패키지에서는 기존 5개 조례 도구 이름을 유지한다. 다만 결과 상태·근거·수집범위가 추가되고, 기관명은 정확 일치로 바뀌며, 비교 시 식별자가 없으면 후보 선택을 요청한다. 문자열 JSON에서 구조화된 결과로 반환 형식도 달라진다. 도구 목록을 갱신하고 기존 호출을 점검해야 한다.

백업 대상은 현재 소스, 배포 시작 명령, 환경변수의 이름과 저장 위치, MCP 연결 설정이다. 비밀값을 문서·화면 캡처·공개 저장소에 복사하지 않는다.

## 2. 법제처 API 준비

공식 신청 페이지: https://open.law.go.kr/LSO/usrJoin.do

국가법령정보 공동활용에서 본인 계정으로 API 이용을 신청하고 인증값과 요청 IP 관련 설정을 확인한다. `LAW_OC`에는 **신청·발급 또는 지정한 API 인증값**을 넣는다. 예전 예제의 `test`를 실제 인증값처럼 사용하거나, 임의로 이메일 아이디를 정답으로 간주하지 않는다. 신청 화면과 공식 안내의 현재 요구사항을 따른다.

실제 호출은 배포 서버에서 발생한다. API 서비스에 등록한 요청 IP와 배포 서버의 송신 IP가 다르면 개인 PC에서 되더라도 서버에서 실패할 수 있다. 배포 환경이 고정 송신 IP를 제공하는지, 등록 가능한 형태인지를 해당 환경과 API 포털에서 확인해야 한다.

본 패키지는 다음 공식 API를 사용한다.

| 용도 | target | 주요 식별자 |
|---|---|---|
| 자치법규 검색·본문 | `ordin` | 목록 검색, 본문 `ID` 또는 `MST` |
| 현행 시행일 기준 법령 | `eflaw` | 현재 `ID`, 특정 버전 `MST+efYd` |
| 공포일 기준 법령 | `law` | `ID` 또는 `MST` |
| 상위법 연결 조례 | `lnkLsOrd` | `knd=법령ID` |
| 조문 연결 조례 | `lnkLsOrdJo` | `knd`, `JO` 4자리, `JOBR` 2자리 |

공식 포털이 JSON 대신 XML을 반환하는 경우 안전한 XML 파서를 사용한다. 인증 실패·형식 오류·빈 응답은 “조례 없음”으로 바꾸지 않는다.

## 3. 로컬 설치

기관이 승인한 Python 3.11 이상 환경에서 프로젝트 폴더를 연다.

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:LAW_OC = "본인_API인증값"
.venv\Scripts\python.exe -m jachi.cli doctor
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe scripts/smoke_mcp.py
.venv\Scripts\python.exe scripts/live_check.py
```

`doctor`는 비밀값이 아니라 설정 여부와 패키지 버전만 출력한다. `smoke_mcp.py`는 실제 MCP 연결·도구 조회·상태 도구를 시험한다. `live_check.py`는 법제처에서 지방자치법을 검색·조회하므로 본인 API 인증값이 필요하다.

제작 환경에서는 MCP SDK가 설치되지 않아 SDK 통합시험을 실행하지 못했다. 위 설치 후 동일 시험이 통과하는지 확인하고, 실패 시 운영에 반영하지 않는다.

MCP SDK는 원본의 FastMCP 1.x 흐름을 유지했다. 공식 SDK의 현재 주 배포는 2.x이므로 무조건 최신 버전을 설치하지 않고 `mcp>=1.28,<2` 범위로 제한한다. 이는 전체 의존성 잠금파일이 아니다. 설치·통합시험 후 기관 환경에서 정확한 버전을 잠그고 보안 업데이트 절차를 운영해야 한다.

## 4. 로컬 MCP 등록

`examples/mcp-stdio.template.json`에서 `command`를 가상환경 Python의 절대경로로, `args`를 `jachibeopgyu_mcp.py`의 절대경로로 바꾼다. `LAW_OC`는 클라이언트가 서버 프로세스에 전달하는 환경변수로 설정한다.

서버 기본 실행은 STDIO이다. 단순 실행 후 화면에 아무 안내가 없을 수 있으며, 일반 메시지를 STDOUT에 출력하지 않는 것이 정상이다. MCP 호스트가 표준입출력으로 통신해야 한다.

## 5. 외부 HTTP 또는 Render

빌드 명령:

```text
pip install -r requirements.txt
```

시작 명령:

```text
python jachibeopgyu_mcp.py --http
```

MCP 경로는 `/mcp`, 프로세스 상태 경로는 `/health`이다. `/health`의 정상 응답은 프로세스가 동작한다는 뜻이며 법제처 API·LLM 연결이나 법적 검토의 정상 완료를 보증하지 않는다.

필수/권장 환경변수는 다음과 같다.

| 변수 | 내용 |
|---|---|
| `LAW_OC` | 본인 법제처 API 인증값 |
| `MCP_HOST` | 외부 배포 시 `0.0.0.0` |
| `PORT` | 배포 플랫폼이 제공하는 포트 사용 |
| `MCP_API_TOKEN` | 32자 이상의 무작위 비밀 토큰 |
| `ALLOWED_HOSTS` | 실제 서비스 도메인. 전체 허용 `*` 금지 |
| `ALLOWED_ORIGINS` | 허용할 Origin의 정확한 스킴·도메인 |
| `MCP_PUBLIC_READ_ONLY` | 기본 `false` |
| `ALLOW_EXTERNAL_LLM` | 기본 `false` |

Render의 `RENDER_EXTERNAL_HOSTNAME`이 제공되면 기본 허용 Host/Origin을 이 값으로 구성한다. 커스텀 도메인이나 다른 호스트를 사용하는 경우 명시적으로 설정한다. `render.yaml`에는 자동 토큰 생성과 조례 서버 시작 명령을 넣었다. 기관 승인 Python 버전과 빌드 로그를 함께 확인한다.

`MCP_API_TOKEN`은 서버 접속용이며 `LAW_OC`와 다른 비밀값이다. 클라이언트에서는 `Authorization: Bearer ...` 헤더로 전달한다. `?oc=...`, `?token=...` 형식의 인증 URL은 허용하지 않는다.

**이 서버의 Bearer 검사는 완전한 OAuth 2.1 서버가 아니다.** MCP 클라이언트가 임의 Authorization 헤더를 지원하지 않거나 OAuth 연결만 허용한다면 승인된 OAuth 게이트웨이를 별도로 구성해야 한다. 이 패키지가 모든 호스트 서비스에서 URL만 붙여 넣으면 바로 연결된다고 보장하지 않는다.

HTTP 실연결 시험:

```powershell
$env:MCP_API_TOKEN = "서버와_같은_비밀토큰"
python scripts/smoke_mcp.py --url https://실제-서비스-도메인/mcp
```

실제 토큰을 명령행 URL에 넣지 않는다. 토큰을 외부 문서나 문의 메시지에 붙여 넣지 않는다.

## 6. Gemini 선택 설정

`GEMINI_API_KEY`, `GEMINI_MODEL`, `ALLOW_EXTERNAL_LLM=true`를 서버 환경에 설정한다. 검토 요청에서 `reasoning=gemini`, `allow_external_llm=true`도 지정해야 한다.

기본 모드에는 Gemini 키가 필요 없다. 외부 모델을 사용하는 경우 최대 8회 요청이 발생하며 사용료·한도·자료 처리 조건은 본인 계정과 제공자 정책에 따른다. 특정 모델의 무료 이용 또는 무제한 사용을 전제로 배포하지 않는다.

실호출은 공개된 법령·가상 자료로 먼저 시험한다. 개인정보 의심 패턴이 탐지되면 전송을 막지만, 탐지하지 못한 개인정보가 없다는 보장은 아니다. 기관 승인 없이 비공개 검토서·민원인 자료·내부 결재자료를 넣지 않는다.

## 7. 운영 전 수용시험

실제 자료로 아래 시나리오를 실행하고 결과 원문을 담당자가 대조한다.

| 시나리오 | 통과 조건 |
|---|---|
| 실제 조례 1건 검색·조회 | 기관·정식 제명·ID·시행일·조문 일치 |
| 비슷한 이름의 조례 여러 건 | 첫 결과를 무조건 기준으로 삼지 않음 |
| `서구` 등 모호한 기관명 | 다른 지역으로 임의 연결하지 않음 |
| 현재/시행예정 동일 법령 | `effective`/`promulgated`와 기준일 구분 |
| 구·신 상위법 2개 버전 | 변경 조문과 실제 부칙을 확인 |
| HTTP 403·429·API 장애 | 오류/부분수집 표시, 미제정 결론 없음 |
| 사용자 제공 조례안 | 공식 검증 자료로 승격되지 않음 |
| 변경 원문 해시 불일치 | 개정문 생성 중단 |
| 잘못된 인용·근거 ID | 제안 채택 목록에서 제외 |
| 과거 날짜 검토 | 날짜 입력만으로 역사 버전 검증 완료라 하지 않음 |
| 별표 참조 조례 | 별표 미확보·파일 본문 미수집 경고 |
| 감시 조회 실패 | 이전 성공 스냅샷 유지 |
| 외부 Host/Origin·인증 없음 | 설정에 따라 403/401 거부 |
| 공개 모드 | 내부 문서·종합 검토·개정안 생성 도구 비노출 |

## 8. 정기 감시와 복구

`watch` 명령은 한 번 실행되고 종료한다. `examples/cron.example.txt`는 설치되지 않는 예시다. 기관 승인 스케줄러에서 주기와 시간대를 정하고, 결과의 `changed`와 `unavailable`을 알림 처리한다. 알림 전송 연동은 별도 구현·승인이 필요하다.

SQLite 파일은 영속 디스크에 둔다. 임시 파일시스템의 서버 재시작으로 DB가 사라지면 이전 비교 기준이 없어질 수 있다. 공유 네트워크 파일시스템의 다중 프로세스 쓰기, 대규모 다중 사용자는 별도 DB·인증·요청량 관리 설계가 필요하다.

장애 시 새 버전 반영을 중단하고 이전 배포 소스로 되돌린다. 스냅샷은 복구 목적의 백업을 유지하며, 오류가 난 조회본을 정상 기준으로 수동 덮어쓰지 않는다.
